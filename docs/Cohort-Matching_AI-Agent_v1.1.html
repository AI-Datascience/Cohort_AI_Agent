Technical Architecture Design

大規模行動データにおけるオンメモリ疎行列演算を用いた
ADID抽出アーキテクチャ設計書

Version 2.0 | Scalability Update

1. 目的とスコープ

本ドキュメントは、1,000万件（10M）規模のユニークユーザー（ADID）に対し、2,000次元の行動特徴ベクトルを用いてリアルタイムに近い速度（サブセカンド）でマッチングを行うためのシステムアーキテクチャを定義する。
データソースとしてAzure環境（Delta Lake / Blob Storage）を前提とし、I/Oボトルネックを排除した「オンメモリ疎行列演算モデル」を採用する。

2. 全体アーキテクチャ図

レイテンシを最小化するため、「データ生成（ETL）」と「推論（Inference）」を完全に分離する。推論サーバーは起動時に軽量化された行列データをRAMにロードし、リクエスト時には外部ストレージへのアクセスを一切行わない。

+-------------------------------------------------------+ +-------------------------+ | Data Lake Layer (Azure Storage) | | Inference Layer (API) | | | | | | [Delta Lake (Gold)] [Blob Storage] | | [API Server Instance] | | +---------------+ +-------------------+ | | +-----------------+ | | | Action Logs | | Optimized Matrix | | | | RAM (Memory) | | | | (Parquet/Delta)|------->| (.npz file) |------------>| | [Sparse Matrix] | | | | 10M x 2000 | (A) | Compressed ~2GB | | (B) | | 10M x 2000 | | | +---------------+ Batch +-------------------+ | Load | +-----------------+ | | ^ Convert | at | ^ | | | | Start | | (C) Calc | +----------|--------------------------------------------+ | v | | | [Input Vector] | Daily Updates +-------------------------+ (Data Eng.) ^ | User Req [Context Analysis]

データフロー詳細

  • (A) Batch Optimization: 日次バッチ等でDelta Lakeからデータを抽出し、推論に不要なメタデータを削除。Pythonの scipy.sparse 形式（.npz）に圧縮変換してBlobに配置する。
  • (B) Cold Start Loading: APIサーバーは起動時（またはデプロイ時）にBlobから .npz ファイルをダウンロードし、メモリ空間（RAM）に展開する。
  • (C) On-Memory Calculation: APIリクエスト時は、メモリ内の行列に対して演算を行うため、ディスクI/Oが発生しない。

3. パフォーマンス要件とサイジング

3.1 メモリ要件の試算 (1,000万ADID)

行動データは「多くのユーザーは、2,000箇所のうち数箇所しか訪問しない」という特性を持つため、疎行列（Sparse Matrix）として扱うことでメモリ消費を劇的に削減する。

前提条件:
  • ユーザー数: 10,000,000 ADID
  • 次元数（場所数）: 2,000
  • 平均訪問箇所数: 20箇所/User（Sparsity 99%）
計算式:
データサイズ ≈ 非ゼロ要素数 × (値4byte + インデックス4byte)
= (10M × 20) × 8 bytes ≈ 1.6 GB

結論: 1.6GB〜2.0GB程度のメモリ消費であり、Azure App Service (P1v2以上: 3.5GB RAM) やStandardなコンテナインスタンスで十分にオンメモリ処理が可能である。

3.2 レスポンスタイム予測

処理フェーズ 方式 推定所要時間
データロード RDBMS/Parquet直接参照 数秒 〜 数十秒 (NG)
データロード オンメモリ (本構成) 0 ms (常駐)
行列演算 Dense (密行列) 200〜500 ms
行列演算 Sparse (疎行列・本構成) 10〜50 ms

4. 実装仕様：疎行列化とロード処理

4.1 前処理（Batch Phase: Azure Databricks / Synapse）

Delta Lakeから読み出し、APIサーバーが読み込みやすい形式へ変換する。

import scipy.sparse as sp
import numpy as np

def convert_delta_to_sparse(spark_df):
    """
    Delta LakeのDataFrame(ADID, LocationID, Score)を
    CSR形式の疎行列に変換し、保存する
    """
    # 1. Pandasへ変換 (分散処理後のCollect)
    pdf = spark_df.select("user_idx", "loc_idx", "score").toPandas()
    
    # 2. 疎行列(CSR)の構築
    # rows: user_idx, cols: loc_idx, data: score
    user_count = 10_000_000
    dim_count = 2_000
    
    sparse_matrix = sp.csr_matrix(
        (pdf['score'], (pdf['user_idx'], pdf['loc_idx'])),
        shape=(user_count, dim_count),
        dtype=np.float32
    )
    
    # 3. 軽量ファイルとして保存
    sp.save_npz("/dbfs/mnt/blob_export/user_behavior_matrix.npz", sparse_matrix)
    
    # ※別途、user_idxとADIDの対応表も保存が必要

4.2 推論処理（API Phase: FastAPI / Flask）

サーバー起動時にデータをロードし、リクエストを高速処理する。

import scipy.sparse as sp
import numpy as np

class VectorEngine:
    def __init__(self, model_path):
        print("--- System Boot: Loading Matrix into RAM ---")
        # ディスク(BlobからDL済み)からメモリへロード
        # 1000万件でも数秒でロード完了
        self.user_matrix = sp.load_npz(model_path) 
        print(f"Loaded Matrix Shape: {self.user_matrix.shape}")

    def search(self, location_scores_vector, top_k=100):
        """
        Input: location_scores_vector (1 x 2000) - 商品と場所の関連度
        Output: Top K User Indices
        """
        # [高速演算] 疎行列(10M x 2000) と ベクトル(2000 x 1) の積
        # user_scores は (10M x 1) のベクトルになる
        user_scores = self.user_matrix.dot(location_scores_vector.T)

        # 上位K件のインデックスを取得 (Dense化せずにArgpartition等で高速化推奨)
        # ここでは簡易的にDense化してSort
        scores_dense = user_scores.toarray().flatten()
        top_indices = np.argsort(scores_dense)[-top_k:][::-1]
        
        return top_indices, scores_dense[top_indices]

5. 運用設計（Update Strategy）

課題: データがメモリに常駐するため、行動データの更新時にはAPIサーバーのメモリ内容を入れ替える必要がある。

解決策: Blue/Green デプロイメント
行動データが更新（例：毎朝6時）された際、以下の手順で無停止更新を行う。

  1. バッチ処理で新しい .npz ファイルをBlobに生成。
  2. 新しいAPIインスタンス群（Green環境）を起動。起動スクリプトで最新の .npz をロード。
  3. ヘルスチェック（行列ロード完了）を確認後、ロードバランサーの向き先をBlueからGreenへ切り替え。
  4. 旧インスタンス（Blue）を破棄。

6. 結論

ADID 1,000万件規模へのスケールアップに対し、「ストレージ（Delta Lake）」と「計算リソース（On-Memory API）」を分離するアーキテクチャを採用することで、以下のメリットを享受できる。

  • 超低遅延: I/Oを排除し、マッチング処理を 100ms 未満に抑えることが確実。
  • コスト効率: 疎行列化により、巨大なメモリサーバーを必要とせず、汎用的なインスタンスで稼働可能。
  • データ整合性: Azure Delta Lake を信頼できる唯一の情報源（SSOT）として維持可能。
